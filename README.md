# 訴願審理平台：訴願案件審理 AI 輔助系統

給政府訴願承辦人用的審理工具。承辦人上傳一件訴願案的卷證 PDF，系統自動讀完、判斷這件案子該不該受理、找出相關法條與過往案例，最後產出一份可以直接修改、下載的訴願決定書草稿。

以新北市政府訴願案件為對象開發（黑客松作品），部署在 AWS：Bedrock（Claude Sonnet）負責閱讀、判斷與撰寫，五個 Bedrock Knowledge Base 負責檢索，DynamoDB 存放法條與案例的詳細資料。

> **關於本頁截圖**：AWS 環境已於競賽結束後關閉，截圖是本機以內建樣本重現的操作畫面，僅供展示介面。以下文字說明的都是正式環境（AWS）的實際做法。

---

## 它解決什麼問題

訴願承辦人收到一件案子，要做的事：

1. 從訴願書、原處分書、送達證書、答辯書裡把當事人、日期、處分內容一欄一欄抄出來；
2. 依訴願法第 77 條逐款檢查程序：有沒有逾期、當事人適不適格、是不是行政處分……；
3. 翻法條、翻以前類似的決定書、翻釋字與函釋；
4. 依固定體例寫出決定書。

這些工作重複、耗時，而且一個日期算錯就是整份決定書出錯。本系統把這四步串成一條自動流程，承辦人的角色從「從零開始寫」變成「檢查並修改 AI 的草稿」。

## 整體流程

```mermaid
flowchart TD
    A["上傳卷證 PDF<br/>訴願書／原處分書／答辯書／送達證書"] --> B["文件確認<br/>放錯槽標出，掃描檔走 OCR"]
    B --> C["案件資訊擷取<br/>約 65 個欄位、案由、爭點、援引法條"]
    C --> D{"程序審查<br/>訴願法第 77 條"}
    D -- 受理 --> E["過往案例檢索"]
    D -- 不受理 --> E2["同類不受理案例檢索"]
    E --> F["法規推薦<br/>候選來自過往案例引用的法規"]
    F --> G["釋字／函釋／裁判檢索"]
    E2 --> G
    G --> H["決定書草稿<br/>不受理／駁回／撤銷等五種結果"]
    H --> I["承辦人修改<br/>下載 PDF／Word"]
```

上傳後整條流程在背景自動跑完，可切換至其他畫面操作。重跑有三個起點：文件確認頁可從案件資訊擷取開始整條重跑；改了案件資訊，可從程序審查往後重跑；改了程序審查結論，可從參考依據往後重跑。起點之前的結果保留不動。

### 2. 上傳卷證，上傳即開始分析

四個文件槽：訴願書、原處分書、訴願答辯書為必填，送達證書為選填。按下送出後系統立刻在背景跑完整條流程，不必再按「開始分析」；左側「審理歷程」會標出目前跑到哪一階段，畫面自動跟著前進。

![新增案件](docs/screenshots/03-new-case.png)

![分析進行中](docs/screenshots/04-auto-analysis.png)

### 3. 文件確認：放錯檔案會被標出

系統先依文字特徵確認每份 PDF 真的是它所放的那種文件。下面第二張圖故意把原處分書放進「訴願答辯書」槽，系統判斷出「文字特徵更接近原處分書」並建議重新上傳。流程不會因此中斷，是否換檔由承辦人決定；判斷不出來的文件列為待人工核對。

掃描檔（沒有文字層）交給 Claude Sonnet 逐頁轉錄。OCR 讀出來的日期可能有誤，所以這類文件會標上「日期須人工核對原件」；期間計算若依這些日期算出逾期，程式不會拿它去把案件改判為不受理，直到承辦人核對並修改過該份文件的關鍵日期。

![文件確認通過](docs/screenshots/05-document-check.png)

![文件放錯槽](docs/screenshots/06-document-check-reject.png)

### 4. 案件資訊擷取

Claude Sonnet 從四份文件擷取約 65 個欄位，依文件分成五個分頁（訴願書／送達證書／原處分書／訴願答辯書／綜合判讀），欄位排列對照實際公文的印刷格式。「綜合判讀」整理出案由類別、爭點與援引法條：案由類別與爭點是後面檢索的查詢條件，援引法條則直接附進法規推薦清單。

![案件資訊擷取](docs/screenshots/07-f1-extract.png)

![綜合判讀](docs/screenshots/08-f1-summary.png)

所有欄位都能直接修改、自動儲存，日期一律用民國年月日選擇器輸入。承辦人改過資料後，頁首會提示「案件資訊已修改，程序審查尚未依修改後的資料重跑」，按下「AI 生成」即從程序審查往後重跑。第一次修改時，系統會在後端保留模型的原始擷取結果。

![修改後提示重跑](docs/screenshots/09-f1-edited-stale.png)

### 5. 程序審查：依訴願法第 77 條分流

AI 依第 77 條八款逐一檢核，得出「受理」或「不受理（第幾款）」。**訴願期間不交給 AI 算**：以送達證書上的送達日期為起點，由程式依訴願法與行政程序法計算期間末日，並查國定假日表與在途期間表，再與機關收文日比對。算出逾期即改判第 2 款不受理；算出未逾期而 AI 判了第 2 款，則撤銷該款認定並標須人工確認；缺日期算不出來時，才保留 AI 的判斷。卷內沒有送達證書是例外：不計算期間、一律視為未逾期，AI 若判了第 2 款同樣撤銷並標須人工確認。

![程序審查：受理](docs/screenshots/10-screening-admissible.png)

不受理案（寄存送達，依行政程序法第 74 條與釋字 797 號寄存當日即生效，算出已逾期）：

![程序審查：不受理](docs/screenshots/11-screening-inadmissible.png)

### 6. 參考依據：法規、過往案例、釋字、函釋、裁判

五個分頁，每一類都是「先用向量檢索大範圍撈，請 Claude Sonnet 重新排序取前 3 名，詳細資料由資料庫帶出」。法規、過往案例、釋字／函釋／裁判三段的檢索方式依資料特性各自設計，詳見下一節。

- **法規法條**：推薦的條文與全文，另附卷證明文援引的條文，附官方法規資料庫連結，修正日期由資料庫帶出。
- **過往案例**：歷年訴願決定書中最相似的案件與當時的結果，可連回官方查詢系統看全文。
- **司法院釋字／行政函釋／行政法院裁判**：供承辦人論理時參考，可開原文。

## 檢索怎麼設計

三段檢索都走 Bedrock Knowledge Base（Titan Embeddings + S3 Vectors），執行順序是「過往案例 → 法規 → 釋字／函釋／裁判」。先跑過往案例，是因為法規的候選範圍要靠它帶出來。

```mermaid
flowchart LR
    subgraph S1["過往案例"]
        direction TB
        A1["硬篩選<br/>案件類別（不受理案另加結果與款次）"] --> A2["事實、理由兩路查詢<br/>各取 100 個片段"]
        A2 --> A3["RRF 融合<br/>取前 25 件"]
        A3 --> A4["Sonnet 重排<br/>呈現前 3 件"]
    end
    subgraph S2["法規"]
        direction TB
        B1["25 件案例引用過的法規<br/>聯集，上限 50 條"] --> B2["限定在候選內檢索<br/>取 25 個片段"]
        B2 --> B3["Sonnet 重排取前 3"]
        B3 --> B4["加上卷證明文<br/>援引的法條"]
    end
    subgraph S3["釋字／函釋／裁判"]
        direction TB
        C1["三類各自檢索<br/>各取 30 個片段"] --> C2["依文件加總分數<br/>取前 10 份"]
        C2 --> C3["Sonnet 重排<br/>每類取前 3"]
    end
    A3 -. 法規候選 .-> B1
```

### 過往案例

1. **先硬篩選，再比語意**。受理案只在同一案件類別裡找；不受理案再加上「結果為不受理」與「第 77 條同一款」兩個條件。篩完沒有結果時逐層放寬條件（受理案最後一層不加篩選）。
2. **事實、理由兩路查詢**。訴願書的「事實」與「理由」各截 900 字，分別做向量檢索，各取相似度最高的 100 個片段。兩段文字談的是不同的事，合成一段查會互相稀釋。某一欄沒有內容時，該路改用「案由＋首個爭點」查詢。
3. **片段轉成案件排名**。每一路把 100 個片段依案件去重，保留該案第一次出現的名次，得到兩條案件排名。
4. **RRF 融合**。用 Reciprocal Rank Fusion 把兩條排名合成一條，取分數最高的 25 件。兩路都排前面的案件會勝出。
5. **回資料庫查詳細資料**。用案件編號到 DynamoDB 查這 25 件的案號、年度、結果、官方連結、引用法規等欄位。
6. **Sonnet 重排**。把 25 件候選（資料庫欄位加上命中片段）連同案由、爭點交給 Claude Sonnet 依案情相似度重新排序，畫面呈現前 3 件。

這 25 件案例還有第二個用途（僅受理案）：把它們各自引用過的法規取聯集、依出現次數由多到少排序、上限 50 條，交給下一段當法規候選。不受理案不做法規推薦，改用第 77 條與該款相關的固定法條。

### 法規

1. **候選來自過往案例**。同類案件實際引用過的法規，比從整個法規庫裡憑語意撈更準。檢索時限定只在這份候選清單內找。
2. **以「案由＋首個爭點（前 40 字）」查詢**，取相似度最高的 25 個片段（一條法條就是一個片段）。
3. **回 DynamoDB 查條文全文、修正日期、官方連結，再交 Sonnet 重排取前 3 條**。資料庫查不到的條文略過；檢索有命中卻一條都查不到時直接報錯。
4. **加上卷證明文援引的法條**。原處分書與訴願書裡白紙黑字引用的條號，在案件資訊擷取階段就抽出來了，這裡直接到 DynamoDB 精確查詢後附在清單後面，與前 3 條重複的略過。

過往案例沒帶出任何法規時，退回整個法規庫檢索，並在結果上標明「無案例法規可依，改採全庫檢索」，承辦人看得出這筆推薦的來源不同。

### 釋字、函釋、裁判

三類各有自己的 Knowledge Base，做法相同、各自獨立執行，互不影響：

1. **以「案由＋爭點＋理由」截 900 字查詢**，取相似度最高的 30 個片段。
2. **依文件加總分數**。一份釋字或判決會切成很多片段，把同一份文件命中的片段分數加起來，代表整份文件的相關程度，取分數最高的 10 份。
3. **Sonnet 重排取前 3 份**。每份文件拿分數最高的 2 個片段（兩片合計截 600 字）當作判斷依據。
4. **回資料庫查詳細資料**：發文機關、日期、主旨、原文連結。

### 幾個取捨

| 決定 | 理由 |
|---|---|
| 五個 Knowledge Base 不合併 | 法規一條切一片、決定書一段切一片，切法不同；釋字、函釋、裁判分開，三類各取前 3 名時不會互相擠掉 |
| 向量庫只存識別碼，詳細資料放 DynamoDB | 改欄位不必重算向量；條號這種要精確比對的查詢也不適合走語意檢索 |
| 重排用 Claude Sonnet，不用現成的 Rerank API | 需要排序的是「案件」與「文件」，不是片段；先聚合再交給模型排 |
| 模型回傳的排序由程式驗證 | 只接受候選清單內的編號，漏掉的依原順序補上；模型呼叫失敗就讓案件顯示錯誤；模型有回應但編號全不在候選內時，沿用檢索原順序並記錄警告 |
| 過往案例不收「法規引述」與「結語」段落 | 同一部法的上千件案子這兩段幾乎逐字相同，留著只會佔滿檢索名額 |

## 設計重點：AI 不確定的地方，不讓它猜

法律文書錯一個日期或一條法條就是錯的決定，所以系統把「AI 負責的」跟「程式保證的」分開：

| 項目 | 做法 |
|---|---|
| 訴願期間 | 程式依法條計算，查假日表與在途期間表；AI 不決定日期，日期不足算不出來時才保留 AI 的程序判斷 |
| 法條修正日期 | 一律從資料庫帶出，禁止模型生成 |
| 決定書引用的法條 | 決定書的「相關法條」清單只能是可引用清單裡的條文（受理案為法規推薦，不受理案為第 77 條與該款相關法條），程式在生成後過濾；理由欄內文由承辦人核閱 |
| 不受理體例 | 主文套語與事實欄不記載由程式強制（部分不受理部分駁回除外） |
| 訴願書的事實與理由 | 依訴願書上的標題逐字切開；切不出來時才退回模型的結果 |
| 判斷不出來時 | 不硬給答案，案件標為待複核（印章顯示「審理中」）；文件、期間、程序審查的待確認事項與下游未重跑，列在頁首「此案有事實待人工確認，請勿逕行送出」提示區 |
| 人改過的資料 | 案件資訊、程序審查結論、決定結果第一次被改時保留模型原值，程序審查頁並列「系統原判」；案件資訊或程序審查改過後，提示下游尚未重跑 |
| 檢索或資料庫出錯 | 模型呼叫失敗、資料庫限流、法規檢索有命中卻一條都查不到時直接報錯，案件顯示錯誤，不拿空結果充數；個別項目查不到時標「未查得」或略過 |

正確性另以官方訴願決定書做評測：人工抄錄官方決定書的答案，讓系統跑同一件案子的卷證，比對分流結果、決定類型、擷取欄位與期間計算。過往案例庫收錄 110 至 114 年全台各機關的訴願決定書，114 年只拿掉評測用的那批：主辦方資料集裡的 114 年決定書在前處理（`preprocessing/parse_decisions.py`）就排除，不進檢索庫；爬蟲取得的 114 年決定書照常收錄。要把 114 年整年留出時，灌入腳本（`aws_setup/10_ingest_past_decisions.py`）可設 `PAST_DECISIONS_HOLDOUT_YEARS=114`。

## 在本機試用

AWS 環境已關閉，但內建樣本模式不需要任何雲端憑證，有 Docker 就能看到完整操作流程。

```bash
cp .env.example .env
# .env.example 已預設 AI_PROVIDER=mock；編輯 .env 填 API_KEY=0000（登入密碼），
# 並填 POSTGRES_PASSWORD、PGADMIN_EMAIL、PGADMIN_PASSWORD（compose 必填，任意值即可）
docker compose --env-file .env -f docker/docker-compose.yml up --build
```

開啟 http://localhost:8000 ，以 `.env` 的 `API_KEY` 登入。`data_show/demo_cases/` 下有兩組可直接上傳的示範卷證（駁回案、逾期不受理案），即本頁截圖所用的案件。

架構、資料層建置、部署與評測方式見 [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)。
